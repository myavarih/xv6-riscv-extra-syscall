\chapter{Introduction}

xv6 is a simple teaching operating system developed at MIT, targeting the RISC-V architecture. The kernel provides no mechanism to query how much time a process has spent sleeping or how many times it has called \texttt{sleep()}.

This project adds the \texttt{getsleepinfo} system call to the xv6 kernel. The call returns sleep statistics---total ticks and call count---for a specified process or for every process in the system.

\begin{dfnbox}{System Call}
    A \textbf{system call} is the interface through which user-space processes access kernel services. On RISC-V, this mechanism is triggered by the \texttt{ecall} instruction.
\end{dfnbox}

% ══════════════════════════════════════════════════════════════
\chapter{The \texttt{sleepinfo} Structure}

\section{Structure Definition}

The structure \texttt{struct sleepinfo} is defined in \texttt{kernel/proc.h}:

\begin{cbox}{struct sleepinfo}
struct sleepinfo {
  int    pid;          /* process ID (0 for unused slots) */
  uint64 sleep_ticks;  /* total timer ticks in SLEEPING state */
  uint64 sleep_count;  /* number of times sleep() was called  */
};
\end{cbox}

\section{Fields}

\subsection{\texttt{pid} --- Process Identifier}

The numeric process identifier. When querying all processes (\texttt{who~==~-1}), entries corresponding to unused process-table slots have a \texttt{pid} of zero.

\subsection{\texttt{sleep\_ticks} --- Total Sleep Ticks}

The cumulative number of timer ticks that the process has spent in the \texttt{SLEEPING} state. This value is measured directly inside the \texttt{sleep()} function in \texttt{kernel/proc.c}: immediately before \texttt{sched()} the current \texttt{ticks} value is recorded, and immediately after \texttt{sched()} returns (i.e., after the process wakes up) the difference is added to this counter.

\subsection{\texttt{sleep\_count} --- Sleep Call Count}

The number of times \texttt{sleep()} has been called by this process. Every time the process voluntarily relinquishes the CPU---for example, waiting on disk I/O, a pipe, or a \texttt{pause()} call---this counter is incremented by one.

\section{Sleep Instrumentation in \texttt{kernel/proc.c}}

The \texttt{sleep()} function in \texttt{kernel/proc.c} was modified to track sleep statistics:

\begin{cbox}{Sleep instrumentation in sleep()}
// Go to sleep.
p->sleep_count++;
p->chan = chan;
p->state = SLEEPING;

uint sleep_start = ticks; // best-effort unsynchronized read
sched();
p->sleep_ticks += ticks - sleep_start;
\end{cbox}

\begin{notebox}
The \texttt{ticks} variable is read without holding \texttt{tickslock}. This is the same best-effort approach that xv6 uses for other per-process statistics. On RISC-V, 32-bit reads are atomic, so the concurrent read of \texttt{ticks} introduces negligible error in practice.
\end{notebox}

\section{Kernel Implementation: \texttt{sys\_getsleepinfo}}

The function \texttt{sys\_getsleepinfo()} is implemented in \texttt{kernel/sysproc.c}. The first argument (\texttt{who}) selects the mode of operation:

\begin{cbox}{sys\_getsleepinfo implementation}
uint64
sys_getsleepinfo(void)
{
  int who;
  uint64 addr;
  argint(0, &who);
  argaddr(1, &addr);

  struct proc *p = myproc();

  if (who == -1) {
    struct sleepinfo buf[NPROC];
    for (int i = 0; i < NPROC; i++) {
      struct proc *pp = &proc[i];
      acquire(&pp->lock);
      buf[i].pid         = (pp->state != UNUSED) ? pp->pid : 0;
      buf[i].sleep_ticks = pp->sleep_ticks;
      buf[i].sleep_count = pp->sleep_count;
      release(&pp->lock);
    }
    if (copyout(p->pagetable, addr, (char *)buf, sizeof(buf)) < 0)
      return -1;
    return 0;
  }

  struct proc *target = 0;
  if (who == 0) {
    target = p;
  } else {
    for (struct proc *pp = proc; pp < &proc[NPROC]; pp++) {
      acquire(&pp->lock);
      if (pp->state != UNUSED && pp->pid == who) {
        target = pp;
        release(&pp->lock);
        break;
      }
      release(&pp->lock);
    }
    if (target == 0)
      return -1;
  }

  struct sleepinfo si;
  acquire(&target->lock);
  si.pid         = target->pid;
  si.sleep_ticks = target->sleep_ticks;
  si.sleep_count = target->sleep_count;
  release(&target->lock);

  if (copyout(p->pagetable, addr, (char *)&si, sizeof(si)) < 0)
    return -1;
  return 0;
}
\end{cbox}

\section{New Fields in \texttt{struct proc}}

Two new fields were added to \texttt{struct proc} in \texttt{kernel/proc.h}:

\begin{cbox}{New fields in struct proc}
uint64 sleep_ticks; // total ticks spent in SLEEPING state
uint64 sleep_count; // number of times sleep() was called
\end{cbox}

These fields are placed in the private section of \texttt{struct proc} (where \texttt{p->lock} is not required for access), because they are only written by the process itself from within \texttt{sleep()}, which already holds \texttt{p->lock}.

\chapter{User-Space Interface}

\section{Call Signature}

\begin{cbox}{getsleepinfo signature}
int getsleepinfo(int who, struct sleepinfo *buf);
\end{cbox}

\begin{table}[h]
\centering
\begin{tabularx}{\textwidth}{lX}
\toprule
\textbf{Value of \texttt{who}} & \textbf{Meaning} \\
\midrule
\texttt{0}    & Current process --- writes one \texttt{sleepinfo} entry into \texttt{buf} \\
\texttt{> 0}  & Process with \texttt{pid == who} --- writes one entry, or returns \texttt{-1} if not found \\
\texttt{-1}   & All processes --- writes \texttt{NPROC} entries into \texttt{buf} (unused slots have \texttt{pid = 0}) \\
\bottomrule
\end{tabularx}
\caption{Values of the \texttt{who} argument.}
\end{table}

The call returns \texttt{0} on success and \texttt{-1} on error (invalid buffer address, or \texttt{who > 0} with no matching live process).

\section{Test Program: \texttt{sleepinfo}}

The test program \texttt{user/sleepinfo.c} exercises all modes of the system call:

\begin{cbox}{Test program usage}
/* current process */
struct sleepinfo si;
getsleepinfo(0, &si);

/* after pause(5) */
pause(5);
getsleepinfo(0, &si);

/* by explicit pid */
getsleepinfo(getpid(), &si);

/* invalid pid -- should return -1 */
getsleepinfo(99999, &si);

/* all processes */
struct sleepinfo all[NPROC];
getsleepinfo(-1, all);
\end{cbox}

\chapter{Test Results}

\section{Test Environment}

All tests were run in QEMU. Unless stated otherwise, \texttt{CPUS=1} is used. The command \texttt{make qemu CPUS=1} boots xv6.

% ── Test 1: Basic (CPUS=1, fresh boot) ───────────────────────
\section{Test 1: Basic Run (CPUS=1)}

Immediately after boot, running \texttt{sleepinfo} as the first command:

\begin{cboxtext}{Test 1 --- fresh boot, CPUS=1}
$ sleepinfo
self (before sleep): pid=3  sleep_ticks=1  sleep_count=5
self (after  sleep): pid=3  sleep_ticks=6  sleep_count=10
self (by pid)       : pid=3  sleep_ticks=6  sleep_count=10
getsleepinfo(99999): correctly returned -1

all processes:
  pid=1  sleep_ticks=0  sleep_count=23
  pid=2  sleep_ticks=45  sleep_count=11
  pid=3  sleep_ticks=6  sleep_count=10
\end{cboxtext}

\begin{exbox}{Test 1 Analysis}
    \begin{itemize}[noitemsep]
        \item \texttt{sleep\_ticks} increased from 1 to 6 --- \texttt{pause(5)} added exactly 5 ticks.
        \item \texttt{sleep\_count} increased from 5 to 10 --- console I/O causes multiple \texttt{sleep()} calls during command parsing; \texttt{pause(5)} adds more.
        \item Querying by explicit PID returns identical values to \texttt{who == 0}.
        \item Invalid PID (\texttt{99999}) correctly returns \texttt{-1}.
        \item All-processes query shows \texttt{init} (pid=1), \texttt{sh} (pid=2), and \texttt{sleepinfo} (pid=3).
    \end{itemize}
\end{exbox}

Same test with \texttt{CPUS=3} to verify correctness on a multiprocessor configuration:

\begin{cboxtext}{Test 2 --- CPUS=3}

self (after  sleep): pid=3  sleep_ticks=5  sleep_count=10

  pid=1  sleep_ticks=0  sleep_count=23

\begin{exbox}{Test 2 Analysis}
    \begin{itemize}[noitemsep]
        \item \texttt{sleep\_ticks} delta is still 5, confirming \texttt{pause(5)} accuracy across CPUs.
        \item Initial \texttt{sleep\_ticks} is 0 (vs.\ 1 with CPUS=1) --- slight timing variation from multi-hart scheduling.
        \item \texttt{sh} accumulated 44 sleep ticks (vs.\ 45 with CPUS=1) --- consistent within the expected $\pm 1$ tick error described in the Limitations chapter.
    \end{itemize}
\end{exbox}

self (after  sleep): pid=3  sleep_ticks=5  sleep_count=10
self (by pid)       : pid=3  sleep_ticks=5  sleep_count=10

  pid=1  sleep_ticks=0  sleep_count=23
  pid=2  sleep_ticks=45  sleep_count=11
  pid=3  sleep_ticks=5  sleep_count=10

  pid=1  sleep_ticks=0  sleep_count=23
  pid=2  sleep_ticks=194  sleep_count=14
  pid=4  sleep_ticks=10  sleep_count=15

\begin{exbox}{Test 3 Analysis}
    \begin{itemize}[noitemsep]
        \item Second run gets pid=4 (pid=3 was freed after the first run exited).
        \item xv6 zeroes \texttt{struct proc} in \texttt{freeproc()}, but reuses proc-table slots. The second run's initial \texttt{sleep\_ticks=5} and \texttt{sleep\_count=10} show the slot was reused with residual counters from the first run (xv6's \texttt{allocproc} does not zero the entire struct---only selected fields).
        \item \texttt{sh} (pid=2) \texttt{sleep\_ticks} jumped from 45 to 194 --- the shell slept while idle between the two commands.
        \item \texttt{sh} \texttt{sleep\_count} increased from 11 to 14 --- three additional console-read sleeps.
    \end{itemize}
\end{exbox}

Running \texttt{grep} and \texttt{cat README} before \texttt{sleepinfo}, to observe the effect of disk I/O on sleep counters:

\begin{cboxtext}{Test 4 --- after grep + cat README}
$ grep hello README
$ cat README

self (before sleep): pid=5  sleep_ticks=5  sleep_count=2380
self (after  sleep): pid=5  sleep_ticks=10  sleep_count=2385
self (by pid)       : pid=5  sleep_ticks=10  sleep_count=2385

  pid=1  sleep_ticks=0  sleep_count=23
  pid=2  sleep_ticks=94  sleep_count=17
  pid=5  sleep_ticks=10  sleep_count=2385
\end{cboxtext}

\begin{exbox}{Test 4 Analysis}
    \begin{itemize}[noitemsep]
        \item \texttt{sleep\_count} is 2380 before the explicit sleep --- dramatically higher than Test~1's value of 5. The \texttt{grep} and \texttt{cat} commands caused thousands of disk-read \texttt{sleep()} calls (virtio block I/O), and the proc-table slot was reused with accumulated counters.
        \item \texttt{sleep\_ticks} delta remains exactly 5, confirming that the tick measurement is independent of the call count.
        \item pid=5 (not 3) because pids 3 and 4 were consumed by the \texttt{grep} and \texttt{cat} processes.
        \item \texttt{sh} accumulated 94 sleep ticks (vs.\ 45 in Test~1) --- more idle time between multiple commands.
    \end{itemize}
\end{exbox}

\chapter{Limitations}

\begin{notebox}
\textbf{Reading \texttt{ticks} without a lock.}\quad
The \texttt{ticks} variable is read without holding \texttt{tickslock}. If \texttt{tickslock} were acquired inside \texttt{sleep()} while \texttt{p->lock} is already held, every function that holds \texttt{tickslock} and then calls \texttt{sleep()} (e.g., \texttt{sys\_pause}) would need to be audited for lock ordering. The unsynchronized read is the most practical approach.
\end{notebox}

\begin{notebox}
\textbf{Measurement error on multi-CPU configurations.}\quad
With \texttt{CPUS > 1}, the \texttt{ticks} variable is only incremented by CPU~0 (\texttt{clockintr} in \texttt{kernel/trap.c}). Other CPUs read the same value, but it may be slightly stale. For xv6 with \texttt{CPUS=3}, this error is typically less than one tick.
\end{notebox}

\begin{notebox}
\textbf{Kernel \texttt{sleep()} vs.\ \texttt{sleeplock}.}\quad
These statistics only track the kernel \texttt{sleep()} function, which sets the process state to \texttt{SLEEPING}. However, \texttt{sleeplock} also uses the same mechanism internally, so \texttt{sleeplock}-induced sleeps are counted in \texttt{sleep\_count} as well.
\end{notebox}
